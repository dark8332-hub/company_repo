# OpenStack 운영 지원 플랫폼 진행사항

> OpenStack 환경에서 엔지니어가 일일점검, 모니터링, 장애 확인 및 운영 업무를 편리하게 수행할 수 있도록 지원하는 플랫폼의 진행 기록입니다.

## 프로젝트 개요

- 프로젝트명: OpenStack 운영 지원 플랫폼 (가칭)
- 시작일: 2026-08-21
- 현재 단계: 일일점검 화면 고도화(이력·변화 비교·예약 실행) 및 운영 검증
- 대상 사용자: OpenStack 운영 엔지니어 및 관리자
- 문서 상태: 2026-08-31 갱신

## 추진 목표

- 반복되는 일일점검 업무를 자동화한다.
- OpenStack 서비스와 인프라 상태를 한 화면에서 확인할 수 있게 한다.
- 이상 징후와 장애를 빠르게 발견하고 대응할 수 있게 한다.
- 점검 결과와 장애 이력을 누적하여 추적 가능하게 한다.
- 운영 절차를 표준화하고 담당자별 업무 편차를 줄인다.

## 예상 기능 범위

### 일일점검

- OpenStack 주요 서비스 상태 확인
- 컨트롤러, 컴퓨트, 네트워크, 스토리지 노드 상태 확인
- 하이퍼바이저 및 리소스 사용량 확인
- 인스턴스, 볼륨, 네트워크 등 주요 자원 이상 여부 확인
- 점검 결과 저장 및 일일 보고서 생성

### 모니터링

- CPU, 메모리, 디스크, 네트워크 사용량 시각화
- OpenStack API 및 서비스 상태 모니터링
- 임계치 기반 경고와 장애 알림
- 현재 장애 및 과거 이력 조회

### 운영 지원

- 자주 사용하는 운영 명령과 절차 제공
- 장애 대응용 진단 정보 수집
- 작업 및 변경 이력 기록
- 사용자 권한에 따른 기능 제어

### 공급자 연결

- OpenStack 환경의 대표 VIP 등록
- VIP 대상 SSH 연결
- VIP가 연결한 활성 Controller의 호스트명 확인
- 연결된 Controller를 기준으로 OpenStack 환경 및 노드 구성 확인
- 각 노드의 CPU, 메모리, 디스크, 네트워크 자원 상태 수집
- Controller, Compute, Network, Storage 서비스 상태 수집
- 등록된 공급자를 대상으로 일일점검 실행
- 공급자 저장 전 SSH 연결과 수집 가능 항목 확인
- SSH 비밀번호와 개인키를 화면이나 로그에 노출하지 않음

### 공급자 기반 수집 구조

1. 대표 VIP를 통해 활성 Controller에 SSH 연결
2. OpenStack 배포 방식과 사용 가능한 관리 도구 확인
3. Controller에서 노드 및 서비스 목록 수집
4. 접근 가능한 방식에 따라 노드별 자원 상태 수집
5. 수집 결과를 표준 형식으로 변환하여 대시보드에 표시
6. 동일한 수집기를 일일점검 작업에서 재사용

수집 방식은 환경별로 다음 순서로 결정한다.

- 기존 Prometheus 또는 모니터링 시스템이 있으면 해당 메트릭 사용
- OpenStack API/CLI로 하이퍼바이저, 서비스 및 에이전트 상태 확인
- Controller를 점프 호스트로 사용해 각 노드에 SSH 점검
- 배포 방식에 따라 systemd, 컨테이너, Pacemaker/HAProxy 상태 확인

### SSH 및 권한 모델

- 플랫폼은 컨테이너 또는 별도 배포 서버에서 실행한다.
- 플랫폼 실행 위치에서 모든 Controller 및 Compute 노드로 직접 SSH 접속할 수 있다.
- root 로그인을 전제로 하지 않고 sudo 권한이 있는 운영 계정을 사용한다.
- 읽기 전용 점검 명령은 일반 권한으로 실행하고 필요한 명령만 제한적으로 sudo를 사용한다.
- 공급자 연결 시 passwordless sudo 여부와 사용 가능한 관리 도구를 자동 탐지한다.
- 운영 적용 시 점검 명령 전용 sudoers 정책을 제공한다.

## 2026-08-27 OpenStack 점검 장애 확인 결과

### 확인된 실행 상태

- Pacemaker의 `int_vip`, `pub_vip`, `haproxy` 리소스는 현재 `hcon03`에서 실행 중
- 내부 VIP `10.255.191.150/24`는 `hcon03`의 `ens3`에 할당됨
- `hcon03`에서 HAProxy의 `10.255.191.150:15000` 리스닝 확인
- `hcon03` 로컬에서 Keystone `/v3/` 요청 결과 HTTP 200 확인
- `hcon01`, `hcon02`, 플랫폼 배포 서버에서는 `10.255.191.150`의 ARP 상태가 `INCOMPLETE` 또는 `FAILED`
- 다른 노드에서 Keystone VIP 접근 시 `No route to host` 또는 연결 시간 초과 발생

### 영향

- 활성 Controller SSH 연결 자체는 성공함
- Controller에서 OpenStack CLI 실행 시 Keystone 인증 VIP에 접근하지 못해 서비스·리소스 점검이 `확인 불가`로 종료됨
- 다수의 OpenStack CLI 연결 대기 시간이 누적되어 기존 90초 실행 제한을 초과함
- 기존 화면에서는 이 상황을 `활성 Controller SSH 연결 실패: TimeoutError`로 잘못 표시함

### 적용한 개선

- 공급자 VIP의 SSH 포트 상태와 무관하게 등록된 활성 Controller 호스트로 직접 SSH 접속
- Controller 연결 실패 시 선택된 OpenStack 항목을 누락하지 않고 `unavailable` 결과 생성
- OpenStack CLI 일괄 실행 제한을 240초로 확대
- SSH 연결 오류와 SSH 접속 후 명령 실행 제한시간 초과를 별도 문구로 구분
- CLI가 반환한 Keystone/API 오류를 항목 상세 원본 결과에서 확인 가능하도록 유지

### 후속 확인 사항

- `hcon03` 관리망 포트에서 VIP `10.255.191.150`의 allowed-address-pairs 또는 포트 보안 허용 여부
- VIP 이동 후 가상 스위치 및 물리 스위치의 MAC·ARP 학습 상태
- Gratuitous ARP 전달 및 Neutron anti-spoofing 차단 여부
- 네트워크 복구 후 OpenStack 서비스·리소스 전체 항목 재점검

### Middleware MySQL 점검

- `MySQL Host Blocked Errors` 항목 추가
  - 쿼리: `SELECT COUNT_HOST_BLOCKED_ERRORS FROM performance_schema.host_cache;`
  - 판정: 출력값이 모두 0이면 정상, 하나라도 1 이상이면 주의
  - `host_cache`에 행이 없어 출력이 비어 있으면 0으로 변환하지 않고 확인 불가로 표시
- `WSREP Local Cert Failures` 항목 추가
  - 쿼리: `SHOW GLOBAL STATUS LIKE 'wsrep_local_cert_failures';`
  - 판정: 값이 0이면 정상, 1 이상이면 주의
- 두 항목 모두 요약에 실제 판정값을 표시하고 상세 결과에 SQL 원본 출력을 유지

### 공급자별 MySQL 인증

- 공급자 관리 화면에 `DB 인증 등록`·`DB 인증 완료` 관리 UI 추가
- DB 사용자명, 비밀번호, 호스트, 포트를 공급자별로 저장·갱신·삭제
- DB 비밀번호는 기존 Fernet master key로 암호화하며 화면, 공급자 목록, 조회 API에 반환하지 않음
- 점검 실행 시 활성 Controller에 권한 `600`의 임시 MySQL 설정 파일을 생성하고 `mysql --defaults-extra-file=<임시 파일>`로 실행
- 점검 완료 또는 오류 발생 후 임시 설정 파일 삭제를 시도하여 명령줄·로그에 DB 비밀번호가 노출되지 않도록 처리
- 공급자 삭제 시 연결된 DB 인증정보도 함께 삭제
- 현재 `hnti` 공급자의 DB 인증정보는 미등록 상태이며 관리 화면에서 별도 등록 필요

### 실행 안정화

- 동일 공급자에서 점검이 실행 중이면 `409`를 반환하고, 화면은 진행 중인 점검을 따라가다 완료되면 결과를 불러옴
- 예외 발생 시 진행 상태를 `failed`로 남겨 `running` 상태가 고착되지 않도록 처리
- 결과에 `started_at`, `finished_at`, `duration_seconds`, `trigger`를 기록해 소요 시간과 실행 구분 표시
- 일부 항목만 점검한 경우 점검한 항목의 알림만 자동 해소하도록 `sync_check_alerts` 수정
