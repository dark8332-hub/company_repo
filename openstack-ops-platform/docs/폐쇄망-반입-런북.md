# 폐쇄망 반입 런북

컨테이너 런타임이 없는 배포 서버에 OpenStack 운영 지원 플랫폼을 올리고, root 로그인이 막힌 노드를 점검하기까지.

| | |
|---|---|
| 플랫폼 번들 | 1.1.5 |
| 런타임 번들 | nerdctl-full 2.3.5 |
| 대상 | linux/amd64 |
| 반입 용량 | 361MB |
| 기준일 | 2026-09-10 |

**전제 1 · 노드** — 점검 대상 노드는 root 로그인이 차단되어 있고, sudo 권한이 있는 일반 계정만 SSH를 허용합니다.

**전제 2 · 배포 서버** — 배포 서버에 docker·podman·nerdctl이 하나도 없습니다. 런타임부터 반입합니다.

---

## 1. 반입하는 파일

두 개입니다. 성격이 다르므로 따로 묶여 있습니다 — 런타임 설치는 시스템 작업이고, 플랫폼 설치는 아닙니다.
이미 런타임이 있는 사이트는 두 번째 파일만 가져가면 됩니다.

| 파일 | 용량 | 내용 |
|---|---|---|
| `openstack-ops-runtime-2.3.5-offline.tar.gz` | 274MB | 상위 배포처의 `nerdctl-full` 압축 파일을 **다시 묶지 않고 그대로** 담습니다. 사이트에서 상위 배포처의 SHA256으로 직접 검증할 수 있어야 하기 때문입니다. 설치·제거 스크립트와 안내서 포함 |
| `openstack-ops-platform-1.1.5-offline.tar.gz` | 87MB | docker-archive 형식 이미지 tar(적재 후 약 273MB) + `install.sh`·`opsctl.sh`·`lib.sh`·`config.env.example`·`systemd/`·안내서 |

### 런타임 번들 구성

rpm·deb가 아니라 전부 정적 바이너리입니다. RHEL·Rocky·Ubuntu에서 같은 절차로 끝납니다.

| 구성 | 버전 | 구성 | 버전 |
|---|---|---|---|
| nerdctl | v2.3.5 | CNI plugins | v1.9.1 |
| containerd | v2.3.3 | BuildKit | v0.31.2 |
| runc | v1.5.1 | fuse-overlayfs | v1.17 |

### 플랫폼 이미지 구성

`python:3.12-slim` 베이스에 파이썬 패키지 8개뿐입니다.

| 패키지 | 버전 | 패키지 | 버전 |
|---|---|---|---|
| fastapi | 0.116.1 | httpx | 0.28.1 |
| uvicorn[standard] | 0.35.0 | fpdf2 | 2.8.8 |
| asyncssh | 2.21.0 | openpyxl | 3.1.5 |
| cryptography | 50.0.0 | python-multipart | 0.0.32 |

> **알아 둘 것** — 노드 SSH는 `asyncssh`(파이썬 라이브러리)로 직접 말합니다. 이미지에 `openssh-client`가
> 필요 없고, 그래서 `nc`·`ping`·`ssh`·`curl`도 없습니다. 컨테이너 안 진단은 `./opsctl.sh netcheck`로 합니다.

## 2. 배포 서버에 이미 있어야 하는 것

우리가 설치하지 않는 것들입니다. 없으면 설치가 그 자리에서 멈춥니다.

| 항목 | 없으면 |
|---|---|
| x86_64 | **중단** — 이 번들은 amd64 전용입니다 |
| systemd | **중단** — containerd를 서비스로 등록할 수 없습니다 |
| iptables | **중단** — 아래 설명 참조 |
| overlayfs | 경고 — 스냅샷터가 느린 대체 경로로 떨어집니다 |
| tar · sha256sum · awk | **중단** — 압축 해제와 체크섬 검증에 씁니다 |
| root 또는 sudo | **중단** — 런타임 설치는 시스템 작업입니다 |

> **iptables가 특히 중요합니다** — 브리지 네트워크의 포트 매핑은 CNI portmap의 DNAT이고, 밖으로 나가는
> 트래픽은 MASQUERADE입니다. 둘 다 iptables로 이뤄집니다. 없으면 **컨테이너는 뜨는데 화면이 열리지 않고
> 점검도 노드에 닿지 못하는** 반쪽 상태가 됩니다. 폐쇄망 서버는 그 자리에서 iptables를 받을 수 없으므로,
> 설치를 끝내지 않고 멈추면서 `--no-bridge` 경로를 안내합니다.

## 3. 설치 순서

런타임 → 플랫폼 → (선택) 자동 기동. 순서가 바뀌면 플랫폼 설치가 "런타임이 없다"며 멈춥니다.

### ① 런타임 — root 필요

정적 바이너리를 풀고 containerd를 서비스로 등록합니다. 이 단계만 시스템을 고칩니다.

```sh
tar -xzf openstack-ops-runtime-2.3.5-offline.tar.gz
cd openstack-ops-runtime-2.3.5
sudo ./install-runtime.sh

# 브리지 대역(기본 10.4.0.0/24)이 사내망과 겹치면
sudo ./install-runtime.sh --cni-subnet 172.31.240.0/24

# 또는 브리지를 아예 만들지 않고 host 네트워크로 (4장 참조)
sudo ./install-runtime.sh --no-bridge
```

설치 전에 `ip route`와 브리지 대역이 겹치는지 계산합니다. 겹치면 중단합니다 — 겹친 채로 두면
**일부 노드만 점검에 실패하는** 형태로 나타나 원인을 찾기 어렵습니다.

### ② 플랫폼

이미지를 적재하고 컨테이너 하나를 띄웁니다. 번들 디렉터리 밖에는 아무것도 만들지 않습니다.

```sh
cd .. && tar -xzf openstack-ops-platform-1.1.5-offline.tar.gz
cd openstack-ops-platform-1.1.5
cp config.env.example config.env      # HOST_PORT · TIMEZONE · 필요하면 USE_HOST_NETWORK

sudo env "PATH=$PATH" ./install.sh
```

> **`env "PATH=$PATH"`가 핵심입니다** — nerdctl은 `/usr/local/bin`에 있는데 `sudo`가 PATH를 좁혀 그 경로를
> 못 보면, 설치 스크립트가 "런타임이 없다"며 멈춥니다. 런타임을 방금 깐 서버에서 가장 흔한 실패입니다.

6단계(실행 환경 → 설정 → 이미지 적재 → 데이터 → 기동 → 동작 확인)로 진행하고, 마지막에 접속 주소와
계정을 찍습니다. 초기 비밀번호는 `Okestro2018@`이며 첫 로그인에서 변경을 강제합니다.

### ③ 재부팅 자동 기동 — 선택

부팅 직후 컨테이너는 꺼져 있고 자기 자신을 켤 수 없습니다. 켜 줄 것을 하나 둡니다.

```sh
sudo ./opsctl.sh install-service      # 치환 → 검증 → 설치 → enable → 기동
sudo ./opsctl.sh uninstall-service    # 유닛만 제거. 컨테이너는 그대로
```

서식의 자리표시자를 번들 절대경로로 바꾸고, **파일을 놓기 전에** 결과를 검사합니다. 자리표시자가 남았거나
경로가 절대경로가 아니면 설치하지 않고 멈춥니다. 같은 이름의 유닛이 이 번들의 것이 아니면 덮어쓰지 않습니다.
놓은 경로는 `installed-service.txt`에 적히고, 제거는 거기 적힌 것만 지웁니다.

> **1.1.3 이하에서는** 이 명령이 없어 서식을 손으로 치환해야 합니다. 자리표시자는 밑줄 두 개를 포함한
> `__BUNDLE_DIR__` **전체**입니다. `BUNDLE_DIR`만 바꾸면 `__/경로__`가 남아 systemd가
> `path is not absolute`로 유닛을 거부합니다.

> **이 단계가 꼭 필요한가** — 컨테이너는 `--restart unless-stopped`로 떠 있고 nerdctl은 이를 containerd의
> restart 플러그인에 맡깁니다. 그 플러그인이 켜져 있고 containerd가 부팅 시 뜨면 유닛 없이도 복구될 수
> 있습니다. 다만 **실제 재부팅으로는 확인하지 않았습니다.** 재부팅 창이 있으면 유닛 없이 한 번 확인해 보고,
> 없으면 유닛을 두는 쪽이 확실합니다.

## 4. 네트워크 선택 — 브리지 vs host

플랫폼은 컨테이너 안에서 점검 대상 노드로 SSH를 나갑니다. 여기서 막히면 화면은 멀쩡한데 점검만 전부
실패합니다. 먼저 정하고 가는 편이 낫습니다.

| 선택 | 설정 | 이럴 때 |
|---|---|---|
| **브리지** (기본값) | `USE_HOST_NETWORK=no`, HOST_PORT 자유 | 노드가 배포 서버와 같은 대역에 있고, 포트를 8090 말고 다른 값으로 쓰고 싶을 때 |
| **host** (권장) | `USE_HOST_NETWORK=yes`, 포트 8090 고정 | 노드가 사설망 곳곳에 흩어져 있거나, 노드 방화벽이 출발지 IP 기준일 때. 브리지·NAT·포워딩이 통째로 빠지고 컨테이너가 배포 서버 네트워크를 그대로 씁니다. 노드 쪽 허용 규칙도 **서버 IP 하나**로 끝납니다. 런타임 설치의 `--no-bridge`와 짝입니다 |

### 막혔을 때 어느 층인지 보는 법

컨테이너 안과 호스트 양쪽에서 이름 해석 → 경로 → TCP 22 → SSH 배너를 확인하고, 두 결과의 조합으로
조치를 정합니다.

```sh
./opsctl.sh netcheck 10.255.191.11        # 기본 포트 22
./opsctl.sh netcheck controller-01 2222
```

| 컨테이너 | 호스트 | 결론과 조치 |
|---|---|---|
| 성공 | 성공 | 네트워크는 문제가 아닙니다. 계정·키·호스트 키 승인·sudo를 봅니다 |
| 실패 | 성공 | 브리지가 사설망에 닿지 못합니다. `USE_HOST_NETWORK=yes` → `./opsctl.sh restart` |
| 이름 해석 실패 | — | 컨테이너는 호스트 `/etc/hosts`를 물려받지 않습니다. 노드 인벤토리에 **IP를 직접** 넣으세요 |
| 실패 | 실패 | 서버 밖 문제입니다. 라우팅·방화벽·노드 sshd를 봅니다. 컨테이너 문제가 아닙니다 |
| 열림, SSH 아님 | | 포트가 다르거나 앞에 다른 장비가 있습니다 |

출발지 주소도 함께 찍습니다. `10.4.x`로 나가면 브리지를 거쳐 NAT된다는 뜻이라, 둘째 줄을 읽는 근거가 됩니다.

## 5. 노드 접속 — root 차단, sudo 계정만

점검 대상 노드에는 **아무것도 설치하지 않습니다.** 에이전트도 없습니다. 이미 있는 명령(`systemctl`·`pcs`·
`mysql`·`rabbitmqctl`·`openstack`·`ceph`·`ovs-vsctl`·`virsh`·`mount`)을 셸 스크립트로 실행할 뿐입니다.

### 공급자 등록 시 넣는 것

- 계정명
- 개인키 **또는** 비밀번호
- sudo 비밀번호 — 일반 계정은 등록 필요

자격증명은 Fernet으로 암호화되어 `data/providers.db`에 저장되고, 키는 `data/.master_key`입니다.
화면과 로그에는 절대 나오지 않습니다.

### 권한 상승이 일어나는 순서

접속 후 `run_as_root()`가 처리합니다.

1. 저장된 sudo 비밀번호를 확인합니다. 없으면 등록 안내와 함께 중단합니다.
2. `sudo -S -p '' -k -H bash -c`로 실행합니다. 비밀번호는 stdin으로만 전달하고 스크립트는 별도 인자로 전달합니다.
3. 스크립트는 stdin을 `/dev/null`로 고정하고 실제 root 권한과 출력 마커를 확인합니다.
4. 인증 실패 시 확인 불가로 처리합니다. NOPASSWD 자동 선택은 사용하지 않습니다.

> **비특권 실행으로 대체하지 않습니다** — 권한 상승에 실패하면 일반 권한으로 조용히 실행하지 않고
> 확인 불가로 표시합니다. 비특권 실행은 서비스 로그를 읽지 못한 채 **"정상"으로 오판**하기 때문입니다.
> 점검 결과가 틀리는 것보다 안 나오는 편이 낫습니다.

실패 사유는 화면에 구분해서 나옵니다 — sudo 비밀번호 불일치 / sudoers 미등록 / requiretty로 비대화형
sudo 차단 / 비밀번호 필요.

### 노드 쪽에 필요한 것은 셋뿐

- 그 계정의 SSH 로그인
- 그 계정의 sudo 권한과 sudo 인증 비밀번호
- sudoers에 `requiretty`가 없을 것

## 6. 서버에 남는 것과 되돌리기

### 런타임이 남기는 것

전부 `installed-manifest.txt`에 기록되고, `uninstall-runtime.sh`가 **그 목록만** 되돌립니다.
같은 디렉터리에 있던 남의 파일은 건드리지 않습니다.

| 경로 · 설정 | 제거 시 |
|---|---|
| `/usr/local/{bin, libexec/cni, lib/systemd}` | tar 내용 그대로 삭제 |
| `/etc/systemd/system/containerd.service` | 삭제 |
| `/etc/cni/net.d/nerdctl-bridge.conflist` | 삭제 (이미 있었으면 애초에 건드리지 않음) |
| `/etc/modules-load.d` · `/etc/sysctl.d` 각 1개 | 삭제 |
| `net.ipv4.ip_forward`, `net.bridge.bridge-nf-call-iptables` | 0이었던 것만 0으로 복원 |

### 플랫폼이 남기는 것

| 변화 | 되돌리기 |
|---|---|
| 컨테이너 1개 · 이미지 1개 | `./opsctl.sh remove` |
| 번들 안 `data/` (공급자 DB + 마스터 키) | `./opsctl.sh remove --all` |
| systemd 유닛 1개 — ③단계를 실행했을 때만 | `sudo ./opsctl.sh uninstall-service` |

### 전체 제거 (설치의 역순)

```sh
cd /경로/openstack-ops-platform-1.1.5
sudo ./opsctl.sh uninstall-service     # 유닛부터
./opsctl.sh backup                     # 데이터를 남기려면 먼저
./opsctl.sh remove --all               # 컨테이너 · 이미지 · 데이터
cd .. && sudo rm -rf openstack-ops-platform-1.1.5

cd /경로/openstack-ops-runtime-2.3.5
sudo ./uninstall-runtime.sh            # 돌고 있는 컨테이너가 있으면 스스로 중단
```

> **백업 파일 취급** — `backup`이 만드는 tar.gz에는 SSH·MySQL 비밀번호를 푸는 **마스터 키가 들어 있습니다.**
> 접근 통제된 곳에 두거나, 남길 필요가 없으면 함께 지우세요. `data/`는 컨테이너가 root로 쓰므로 디렉터리
> 삭제에 sudo가 필요합니다.

## 7. 확인된 동작

이 서버(운영 서비스가 8090을 쓰는 중)에서 실제로 돌려 본 결과입니다.

| 시나리오 | 결과 |
|---|---|
| 빈 포트 8099로 설치 | 정상 — 로그인·이슈 노트 API 모두 200. 운영 8090은 그대로 200 |
| 운영 중 포트 변경 (8099 → 8098) | 정상 — `config.env` 한 줄 + `restart`. 8099 닫힘, 데이터(providers.db 260KB) 보존 |
| 이미 쓰는 포트(8090)로 설치 | 중단 — 운영 서비스 무영향, 컨테이너 생성 안 됨 |
| 같은 이름의 남의 컨테이너 존재 | 중단 — 그 컨테이너 살아남음 |
| 같은 포트를 다른 이름으로 재설치 | 중단 — 고치기 전에는 둘 다 떠서 포트를 나눠 가졌음 |
| k8s 노드 영향 | 없음 — 전용 namespace(`openstack-ops`) 사용, `k8s.io` 그대로 |

> **기동 확인은 컨테이너 안에서** — 호스트 포트로 확인하면 **같은 포트를 쓰는 다른 서비스가 대신 응답**해
> 기동 실패를 성공으로 보고합니다. 실제로 그랬고, 지금은 컨테이너가 살아 있고 그 안의 앱이 답할 때만
> 성공으로 봅니다. 기동에 실패하면 컨테이너를 정지시킵니다 — `--restart unless-stopped`가 실패를 무한
> 재시작으로 바꾸지 않도록.

## 8. 설치 후 첫 30분

```sh
./opsctl.sh status                     # 런타임 · 컨테이너 · 데이터 한눈에
./opsctl.sh netcheck <컨트롤러 VIP>     # 로그인 전에 SSH 경로부터
./opsctl.sh logs -f                    # 기동이 이상하면
./opsctl.sh restart                    # config.env 를 고친 뒤
./opsctl.sh backup                     # 공급자 등록을 마쳤으면
```

1. `http://<서버IP>:<포트>/` 접속 → `admin` / `Okestro2018@` → 비밀번호 변경(강제)
2. **공급자 연결**에서 대표 VIP·SSH 계정 등록 → SSH 지문 승인 → **연결 진단**으로 VIP·권한 상승·OpenRC·
   Prometheus 한 번에 확인
3. **일일점검**에서 클러스터 노드 탐색 → 점검 실행

노드 이름이 해석되지 않는 사이트라면 탐색 대신 **노드 인벤토리에 IP를 직접** 넣으면 됩니다.
컨테이너는 호스트의 `/etc/hosts`를 물려받지 않습니다.
