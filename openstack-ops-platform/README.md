# OKESTRO OpenStack Operations Platform

OpenStack 운영 엔지니어를 위한 일일점검 및 모니터링 대시보드입니다.

## 빠른 실행

Docker Compose가 설치된 서버에서 다음 명령을 실행합니다.

```bash
docker compose up -d --build
```

실행 후 `http://<서버 주소>:8090`으로 접속합니다.

## 운영 명령

```bash
# 상태 확인
docker compose ps

# 로그 확인
docker compose logs -f dashboard

# 재시작
docker compose restart dashboard

# 종료
docker compose down
```

## 이미지 파일로 전달

인터넷에 연결된 빌드 환경에서 이미지를 생성합니다.

```bash
docker build -t okestro/openstack-ops-platform:latest .
docker save okestro/openstack-ops-platform:latest | gzip > openstack-ops-platform.tar.gz
```

대상 서버로 파일을 전달한 뒤 실행합니다.

```bash
docker load -i openstack-ops-platform.tar.gz
docker run -d \
  --name openstack-ops-platform \
  --restart unless-stopped \
  -p 8090:8090 \
  okestro/openstack-ops-platform:latest
```

## 구성 파일

- `index.html`: 전체 화면(대시보드·일일점검·공급자 연결·인프라 현황·모니터링·알림·작업 이력·설정)을 담은 단일 페이지
- `styles.css`: OKESTRO 남색 테마 및 반응형 스타일
- `js/`: 화면별 모듈. `core.js`(공통 상태·페이지 전환), `dashboard.js`, `inspection.js`, `providers.js`, `infrastructure.js`, `monitoring.js`, `alerts.js`, `history.js`, `settings.js`, `runbooks.js`, `main.js`(초기화)
- `login.html`, `login.js`: 관리자 로그인 및 첫 로그인 비밀번호 변경 화면
- `server.py`: API와 정적 화면 제공, SSH 점검·탐색 실행
- `provider_store.py`: 공급자 인증정보 암호화 저장, 점검 이력·요약·예약 설정, 알림·작업 이력·정비 시간 창, 관리자 계정·로그인 세션, 운영 설정과 감사 로그 관리
- `inventory_collector.py`: 노드 인벤토리 수집 스크립트와 파서(네트워크 비의존)
- `inspection_report.py`: 점검 내용·이상 항목 보고서 PDF 생성(fpdf2)
- `inspection_excel.py`: 운영자 점검표 양식 Excel(xlsx) 생성(openpyxl)
- `runbooks.py`: 점검 항목별 조치 가이드(런북) 기본 문서
- `tests/`, `pytest.ini`: API 회귀 테스트와 JS 스모크 테스트
- `fonts/`: PDF 한글 출력용 NanumGothic 글꼴(OFL 라이선스)
- `nginx.conf`: 배포용 웹 서버 설정
- `Dockerfile`: 컨테이너 이미지 정의
- `compose.yaml`: 운영 실행 구성
- `PROGRESS.md`: 프로젝트 진행 기록

## 로그인

모든 화면과 API는 관리자 로그인이 필요합니다(`/api/health`만 예외). 계정은 관리자 1개이며 로그인 세션은 서버(SQLite)에 저장되고 HttpOnly 쿠키로 유지됩니다.

| 환경 변수 | 기본값 | 의미 |
|---|---|---|
| `ADMIN_USERNAME` | `admin` | 관리자 아이디(영문·숫자·`._-` 2~64자) |
| `ADMIN_PASSWORD` | `Okestro2018@` | 첫 시작 시 계정을 만들 초기 비밀번호. 비워두면 기본값 `Okestro2018@`를 사용합니다 |
| `ADMIN_PASSWORD_RESET` | 없음 | `1`로 두고 `ADMIN_PASSWORD`를 채워 재시작하면 비밀번호를 강제로 교체하고 모든 세션을 해제합니다. 로그인 후 반드시 다시 비웁니다 |
| `SESSION_TTL_HOURS` | 8 | 로그인 유지 시간 |
| `SESSION_COOKIE_SECURE` | 없음 | `1`이면 쿠키에 `Secure`를 강제합니다. HTTPS 또는 `X-Forwarded-Proto: https` 뒤에서는 자동 적용됩니다 |

- 초기 비밀번호(기본 `Okestro2018@`)로 처음 로그인하면 새 비밀번호 설정을 요구합니다(8자 이상, 영문·숫자·특수문자 중 두 종류 이상). 계정이 만들어진 뒤에는 `ADMIN_PASSWORD`를 바꿔도 반영되지 않습니다.
- 비밀번호는 `설정 > 관리자 계정`에서 변경하며, 변경하면 다른 브라우저의 로그인은 모두 해제됩니다. 왼쪽 사이드바 하단과 설정 화면에서 로그아웃할 수 있습니다.
- 같은 주소에서 로그인에 5회 연속 실패하면 300초 동안 차단됩니다. 로그인 성공·실패는 서버 로그에 남습니다.
- 비밀번호는 `scrypt` 해시로만 저장되고 세션 토큰도 해시로 저장됩니다. 현재 HTTP로 서비스하면 비밀번호가 평문으로 전송되므로 사이트 배포 시 앞단 TLS 적용을 권장합니다.
- `curl`로 API를 호출할 때는 먼저 `POST /api/auth/login`으로 받은 쿠키를 사용합니다.

```bash
curl -c cookie.txt -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<비밀번호>"}' http://<서버 주소>:8090/api/auth/login
curl -b cookie.txt http://<서버 주소>:8090/api/providers
```

## 대시보드

대시보드는 선택한 공급자의 `GET /api/providers/{id}/overview` 응답으로 구성됩니다. 점검 항목마다 그 항목을 마지막으로 점검한 결과를 사용하므로 일부 항목만 선택한 부분 점검을 실행해도 나머지 항목이 사라지지 않습니다. KPI 카드, 서비스 항목, 이상 항목, 알림, 추이 차트를 클릭하면 관련 화면으로 이동합니다. 인프라 현황도 같은 API를 사용합니다.

화면 최상단에는 `GET /api/overview`로 등록된 모든 공급자의 최신 점검 시각·상태·이상 건수·활성 알림을 한 줄에 보여주는 통합 카드와 오늘의 할 일(오늘 예약 점검의 실행 여부, 미확인 위험 알림, 오늘 예정된 작업)이 표시됩니다. 카드를 클릭하면 해당 공급자를 선택해 아래 상세로 이동합니다.

## 모니터링

모니터링 화면은 Controller(또는 VIP)의 9090 포트에서 Prometheus를 자동으로 찾아 node_exporter 지표로 CPU·메모리·루트 디스크 사용률, 네트워크 송수신, Load, 가동 시간과 job별 수집 대상 상태를 표시합니다. 조회 범위는 1시간·6시간·24시간·7일이며 30초 자동 갱신을 켤 수 있습니다. Prometheus가 없는 환경에서는 일일점검 이력의 노드 자원 수치를 점검 시각별로 대신 표시합니다. node_exporter의 job 이름은 `node_exporter`를 기본으로 봅니다.

자동 탐지로 찾지 못하거나 포트·인증이 다른 환경에서는 `모니터링 연결` 설정에서 공급자별로 Prometheus 주소, 인증 방식(없음·기본 인증·베어러 토큰), TLS 검증 여부와 Grafana·Alertmanager 주소를 등록합니다. 자격증명은 SSH 인증정보와 같은 방식으로 암호화 저장되며 화면과 API에 반환되지 않습니다. `연결 테스트`로 저장 전에 확인할 수 있습니다.

다음 항목이 함께 제공됩니다.

- 임계치 알림 규칙: 지표와 기준값·지속 시간을 등록하면 초과 시 알림 및 장애가 자동으로 생성되고 값이 정상으로 돌아오면 해소됩니다. 대상 노드에 정비 시간 창이 열려 있으면 억제됩니다.
- 노드 상세: 노드를 클릭하면 파티션별 디스크, 인터페이스별 트래픽, iowait, swap 등 상세 차트를 봅니다.
- OpenStack 계층: 플랫폼에서 OpenStack API 응답을 직접 확인하고, Prometheus에 지표가 있으면 HAProxy 백엔드 상태, RabbitMQ 큐 적체, Galera 상태를 함께 표시합니다.
- Alertmanager가 등록되어 있으면 발화 중인 알림을, 필요하면 자유 PromQL 조회 결과를 표시합니다.

## 보고서 저장(PDF·Excel)

일일점검 화면 상단의 `PDF 저장`을 누르면 주의·확인 불가 항목의 판정 근거와 원본 결과를 담은 이상 항목 보고서가 `일일점검_이상항목_<공급자>_<날짜-시각>.pdf`로, `점검 내용 보기`의 `PDF 저장`을 누르면 전체 점검 내용이 `일일점검_<공급자>_<날짜-시각>.pdf`로 서버에서 생성되어 바로 내려받아집니다. 브라우저 인쇄 대화상자는 사용하지 않습니다. 한글 글꼴은 이미지에 포함된 `fonts/` 디렉터리의 NanumGothic을 사용합니다.

`Excel 저장`은 운영자가 쓰던 점검표 양식(번호 붙은 섹션 제목과 점검 분류·점검 사항·점검 방법·점검 결과·특이사항 표)을 그대로 재현한 `일일점검_<공급자>_<날짜-시각>.xlsx`를 내려받습니다.

## 일일점검 예약 실행

일일점검 화면의 `예약 실행` 패널에서 공급자별로 매일 실행할 시각과 점검 항목을 저장하면 서버가 해당 시각에 자동으로 점검을 실행하고 알림을 갱신합니다. 시각은 `INSPECTION_TIMEZONE` 환경 변수(기본 `Asia/Seoul`)를 기준으로 해석하며 `compose.yaml`에서 변경할 수 있습니다. 예약 결과는 점검 이력에 `예약` 구분으로 기록되고, 같은 공급자의 점검이 이미 실행 중이면 해당 날짜의 예약 실행은 건너뜁니다.

## root가 아닌 sudo 계정으로 점검

root SSH 접속이 차단된 환경에서는 sudo 권한이 있는 운영 계정으로 공급자를 등록합니다. 일일점검 명령(로그 파일 읽기, `pcs`, `rabbitmqctl`, `virsh`, `ovs-vsctl`, `smartctl`, `dmesg` 등)은 root 권한이 필요하므로 서버가 모든 점검 스크립트를 `sudo`로 실행합니다. 등록 계정이 root이면 기존과 같이 직접 실행됩니다.

- 노드에서 비밀번호 없는 sudo(NOPASSWD)가 허용되면 별도 설정 없이 `sudo -n`으로 실행됩니다.
- NOPASSWD가 허용되지 않으면 등록 화면의 `sudo 비밀번호`를 입력합니다. 비밀번호 인증 계정은 비워두면 SSH 비밀번호로 sudo를 시도합니다. 등록 시 VIP의 Controller에서 `sudo -S -k true`로 비밀번호를 검증한 뒤 SSH 인증정보와 함께 암호화 저장하며 화면과 API에 반환하지 않습니다.
- 등록 후에는 공급자 목록의 `sudo 비밀번호 등록` 버튼(`sudo 인증 관리`)에서 비밀번호를 등록·교체·삭제할 수 있습니다.
- 점검 시 노드마다 `sudo -k -n true`로 NOPASSWD 여부를 먼저 확인하고, 비밀번호가 필요한 노드에서만 `sudo -S -p '' -k -H bash -s`의 표준입력 첫 줄로 비밀번호를 전달합니다. root 권한을 얻지 못한 노드는 일반 권한으로 대신 실행하지 않고 `SSH 점검 실패: root 권한 획득 실패` 사유와 함께 확인 불가로 표시됩니다. 일반 권한으로 실행하면 읽지 못한 로그가 오류 0건(정상)으로 잘못 판정되기 때문입니다.
- 대상 노드의 sudoers에 `requiretty`가 설정되어 있으면 비대화형 sudo가 차단되므로 해당 계정에 `Defaults:<계정> !requiretty`를 적용해야 합니다. OpenStack CLI는 `sudo -H`로 `HOME=/root`가 되어 `/root/contrabass-openrc`를 그대로 사용합니다.

## 일일점검 실행과 확인

- **판정 임계치**: CPU·메모리·디스크 경고 비율과 로그 오류 허용 건수를 공급자별로 설정합니다. 저장하지 않으면 기본값(80%)을 사용합니다.
- **기본 점검 항목**: 자주 쓰는 항목 조합을 공급자별 기본값으로 저장해 화면을 열 때마다 다시 고르지 않습니다.
- **실행 취소**: 점검이 진행 중일 때 진행률 패널의 `취소`를 누르면 실행 중인 SSH 명령이 끝나는 대로 중단합니다. 패널에는 노드별 진행 상태가 함께 표시됩니다.
- **조치 가이드(런북)**: 결과 상세와 알림에서 항목별 조치 가이드를 엽니다. `확인 순서 → 원인 후보 → 조치 → 확인` 순서의 기본 문서가 내장되어 있고, 사이트 사정에 맞게 공급자별로 내용을 바꿀 수 있습니다.

## 공급자 수정·연결 진단·노드 관리

- 공급자 이름, VIP, 계정, SSH 키는 `수정`에서 교체합니다. 삭제 후 재등록할 필요가 없으므로 점검 이력이 유지됩니다.
- `연결 진단`은 VIP 도달, 호스트 키 신뢰, SSH 로그인, root 권한 상승, OpenRC와 OpenStack CLI, 노드 도달, Prometheus 발견, DB 인증정보 등록 여부를 한 번에 확인하고 실패한 항목의 조치 방법을 알려줍니다. 새 사이트를 등록한 직후에 먼저 실행하기를 권장합니다.
- `노드 관리`에서 탐색되지 않은 노드를 직접 추가하거나 역할을 고치고, 정비 중인 노드를 점검 대상에서 제외할 수 있습니다. `nova-compute`가 없어 Compute가 자동 탐색되지 않는 환경에서 사용합니다.
- 사이트·환경·담당자·태그를 공급자 프로필로 기록해 사이트가 늘어나도 구분할 수 있습니다.

## 알림과 정비 시간 창

- 알림은 원인별로 묶여 표시됩니다. Controller SSH 실패 하나로 확인 불가가 수십 건 발생해도 1건으로 보이고 하위 항목을 펼쳐 봅니다.
- 각 알림에는 상태·담당자 변경과 코멘트가 시간순 타임라인으로 남고, 여러 건을 골라 한 번에 확인·해소할 수 있습니다. 반복 발생 건수와 평균 확인·해소 시간은 통계에서 봅니다.
- `정비 시간 창`에 기간과 대상 공급자를 등록하면 그 시간 동안 알림이 억제되고 작업 이력과 연결됩니다. 계획된 작업 때문에 알림이 쌓이는 것을 막습니다.

## 작업 이력

작업은 `예정 → 진행 → 완료 → 승인` 순으로 상태를 옮기며 기록합니다. 작업자는 로그인 계정으로 채워집니다. 작업 시작·완료 시점에 점검을 실행해 작업에 연결하면 변경 전후 결과 차이를 그대로 확인할 수 있고, 관련 파일을 첨부하거나 월간 보고서를 CSV로 내려받을 수 있습니다.

## 설정과 감사 로그

- 점검 실행 제한 시간, 점검 이력 보관 정책, 예약 실행 기준 시간대, 감사 로그 보관 기간은 설정 화면에서 수정하고 서버(SQLite)에 저장합니다. 값을 지우면 환경 변수 기본값으로 돌아갑니다.
- 왼쪽 메뉴 표시 항목과 대시보드 구성은 계정별로 서버에 저장되므로 다른 PC에서 로그인해도 유지됩니다.
- 감사 로그는 로그인, 공급자 등록·수정·삭제, 인증정보 변경, 점검 실행, 알림 처리, 작업 이력, 설정 변경 등을 누가 언제 어떤 결과로 했는지 기록합니다. 설정 화면에서 행위자·동작·대상·기간으로 조회하며, 보관 기간(기본 365일)이 지난 기록은 자동으로 정리됩니다.

## 테스트

```bash
.venv/bin/python -m pytest
```

API 회귀 테스트와 JS 스모크 테스트를 실행합니다. JS 스모크는 최소 DOM을 흉내 낸 환경에서 `js/`의 모든 모듈을 실행해 구문 오류와 초기화 예외를 잡습니다.

## 로그 오류 제외 패턴

일일점검의 예외 처리 패널 아래 `로그 오류 제외 패턴`에서 공급자별로 정규식을 등록하면, 각 노드가 전날·전전날 로그를 검색할 때 `grep -E`(대소문자 구분 없음)로 일치하는 줄을 걸러내고 오류 건수와 신규·해소 비교에서 제외합니다. 서비스를 `전체 로그`로 두면 모든 로그 항목에 적용됩니다. 제외된 줄 수는 특이사항에 `제외 패턴 N건`으로 남으므로 실제 오류가 가려지지 않았는지 확인할 수 있습니다. 등록 시 정규식이 Python과 `grep -E` 양쪽에서 해석되는지 검증합니다.

## 점검 제한 시간

원격 명령마다 개별 제한 시간이 적용되어 한 명령이 멈춰도 해당 항목만 `확인 불가`가 되고 나머지 결과는 유지됩니다. 설정 화면의 `점검 실행 제한 시간`에서 값을 직접 수정할 수 있고, 저장하면 재기동 없이 반영됩니다. 아래 환경 변수는 저장된 값이 없을 때 쓰이는 기본값이며 `기본값으로 되돌리기`를 누르면 다시 이 값을 사용합니다.

| 환경 변수 | 기본값 | 적용 대상 |
|---|---|---|
| `INSPECTION_COMMAND_TIMEOUT` | 20 | 노드 시스템 명령 1개 |
| `INSPECTION_LOG_TIMEOUT` | 45 | 노드 로그 검색 1개 서비스 |
| `INSPECTION_OPENSTACK_TIMEOUT` | 45 | 활성 Controller의 openstack CLI·pcs·rabbitmqctl·mysql 명령 1개 |
| `INSPECTION_NODE_TIMEOUT` | 240 | 노드 스크립트 전체 |
| `INSPECTION_CONTROLLER_TIMEOUT` | 600 | 활성 Controller 스크립트 전체 |
| `INSPECTION_NODE_CONCURRENCY` | 8 | 동시에 점검하는 노드 수 |

항목별 소요 시간은 상세 결과의 `소요` 배지와 결과의 `timing`에 기록됩니다. 일일점검 화면의 `소요 시간 통계`에서 최근 점검들의 항목·노드별 소요 시간과 관측값에서 계산한 제한 시간 권장값을 확인해 위 값을 조정할 수 있습니다.

## 점검 이력 보관 정책

점검 결과는 다음 정책으로 자동 정리됩니다(서버 시작 시와 24시간마다, 점검 실행 중에는 건너뜀). 설정 화면의 `점검 이력 보관`에서 정책을 수정하고 저장 현황을 보며 `지금 정리`로 즉시 실행할 수 있습니다. 아래 환경 변수는 저장된 값이 없을 때의 기본값입니다.

| 환경 변수 | 기본값 | 의미 |
|---|---|---|
| `INSPECTION_RETENTION_KEEP` | 10 | 공급자별 최신 N건은 항상 원본 그대로 보존 |
| `INSPECTION_RAW_RETENTION_DAYS` | 30 | 지난 결과는 원본 출력(명령 출력·로그 표본)을 정리하고 상태·판정·건수만 보관 |
| `INSPECTION_RETENTION_DAYS` | 180 | 지난 결과 삭제 |
| `INSPECTION_RETENTION_MAX` | 200 | 공급자별 최대 보관 건수, 초과분은 오래된 순으로 삭제 |

값을 0으로 두면 해당 규칙을 사용하지 않습니다. 원본이 정리된 결과는 화면 상세에 안내가 표시되며 이력·변화 비교·추이 차트에는 계속 포함됩니다.

## 공급자 데이터 보관

등록된 공급자와 점검 이력은 컨테이너의 `/app/data/providers.db`에 저장됩니다. SSH 개인키와 비밀번호는 `/app/data/.master_key`로 암호화되며 API와 화면에 반환되지 않습니다.

VIP가 다른 Controller로 이동해 SSH 호스트 키가 달라진 경우 공급자를 다시 등록하지 않습니다. 공급자 화면의 `SSH 키 관리`에서 현재 지문을 조회하고 대상 Controller에서 직접 확인한 값과 일치할 때만 신뢰 목록에 추가합니다. 승인 전에는 SSH 사용자 인증을 시도하지 않으며 지문 승인과 폐기 이력이 데이터베이스에 기록됩니다.

Compose 실행 시 `provider-data` 볼륨이 연결되므로 컨테이너를 재시작하거나 교체해도 데이터가 유지됩니다. 백업할 때는 데이터베이스와 암호화 키를 반드시 함께 보관해야 합니다.

```bash
docker run --rm \
  -v openstack-ops-platform_provider-data:/data \
  -v "$PWD":/backup \
  alpine tar -czf /backup/provider-data-backup.tar.gz -C /data .
```
